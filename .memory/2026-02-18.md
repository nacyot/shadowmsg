## push 증분 전송 아키텍처

`tags: push, architecture, luahome, watermark`
`files: src/services/push.ts, src/stricli/push.ts, src/services/database.ts`

shadowmsg에서 LuaHome 서버로 iMessage를 벌크 전송하는 시스템을 완성했다.

- `push_state` 테이블에 endpoint별 `last_pushed_rowid`를 저장하여 증분 전송
- 500건 단위 배치로 POST /api/v2/messages/bulk에 전송
- 배치마다 push_state 업데이트 (부분 성공 허용)
- `--full` 플래그로 push_state 리셋하여 전체 재전송 가능

sender 필드는 search.ts의 기존 COALESCE 패턴을 재사용: `COALESCE(alias, name, org, handle.id)`. 이 패턴은 `src/services/search.ts:78`에서 검색 기능에도 동일하게 사용하고 있어서, 표시 이름 해석 로직을 한곳에서 관리할 수 있다.

push_state 테이블은 database.ts의 initializeSchema()에 넣지 않았다. push는 선택적 기능이므로 `ensurePushStateTable()`로 push 서비스가 처음 호출될 때 `CREATE TABLE IF NOT EXISTS`를 실행하는 게 맞다.

## push API 필드 매핑 불일치: external_id 타입, sender/sender_name 역전

`tags: bug, api-contract, luahome, cross-repo, field-mapping`
`files: src/services/push.ts`
`related: lua_home/app/controllers/api/v2/messages_controller.rb`

LuaHome 서버와 shadowmsg 사이에 API 계약 불일치 3건이 있었다.

| 필드 | shadowmsg가 보낸 것 | LuaHome이 기대한 것 | 결과 |
|------|---------------------|---------------------|------|
| external_id | `"imessage-45001"` (문자열) | 정수 (`.to_i` 변환) | 0으로 변환 → 전부 skip |
| sender | 표시 이름 ("Alice") | 전화번호 ("+1234567890") | 의미 역전 |
| sender_name | 미전송 | meta jsonb에 저장 기대 | 누락 |

external_id가 가장 치명적이었다. Ruby의 `"imessage-45001".to_i`는 0을 반환하고, 서버는 external_id=0인 레코드가 이미 존재한다고 판단해 전부 skip했다.

교훈: 클라이언트와 서버가 별도 저장소일 때, 필드 타입과 의미를 양쪽 코드에서 cross-reference하여 사전 검증해야 한다. 플랜 문서만으로는 이 수준의 불일치를 잡기 어렵다.

## bunx 배포 방식 결정: launchd PATH 제약과 bun:sqlite 의존성

`tags: deployment, bunx, launchd, bun, decision`
`files: src/stricli/service.ts`

다른 Mac에서 주기적으로 push를 실행해야 해서 배포 방법을 논의했다.

**제약 조건**:
- shadowmsg는 `bun:sqlite`을 import하므로 Node.js/npx 실행 불가 (`import { Database } from 'bun:sqlite'` — `src/services/database.ts:1`)
- launchd LaunchAgent의 PATH는 `/usr/bin:/bin:/usr/sbin:/sbin`만 제공. 셸 프로파일(`.zshrc`)을 읽지 않으므로 mise, homebrew, bun 전부 PATH에 없음
- HOME은 LaunchAgent이면 제공됨

**검토한 옵션**:
1. `bun build --compile`로 단독 바이너리 → o3는 "가장 안정적"이라고 추천했지만 bun:sqlite 네이티브 모듈 호환성 불확실
2. mise shim 절대경로(`~/.local/share/mise/shims/bun`)를 plist에 지정 → 환경 의존적, mise가 없는 Mac에서 실패
3. **bunx** → bun만 설치하면 됨, npm 패키지를 다운받아 bun 런타임으로 실행

**결정**: 3번. `which bunx`로 절대경로를 확보해서 plist의 ProgramArguments에 직접 넣는다. `~`는 which가 항상 절대경로를 반환하므로 들어갈 일 없음. 로컬 npm 레지스트리(`npm.app.local`)에 `@home/shadowmsg`로 배포.

Bun 설치 경로는 설치 방법에 따라 다르다:
- homebrew: `/opt/homebrew/bin/bunx`
- curl 스크립트: `~/.bun/bin/bunx` (절대경로: `/Users/<user>/.bun/bin/bunx`)

## oclif→stricli 마이그레이션 완료: 이중 엔트리포인트 해소

`tags: migration, oclif, stricli, cleanup`
`files: bin/run.js, src/app.ts, src/cli.ts`
`deleted: src/commands/*, src/index.ts, src/base-command.ts`

**이전 상태**:

## cross-device ROWID 중복: 같은 메시지에 다른 external_id

`tags: deduplication, bug, unresolved, luahome-server, rowid`
`files: src/services/push.ts`
`related: lua_home/app/models/messages_raw.rb (sha256_hash 생성 로직)`

같은 iMessage가 두 Mac에서 각각 다른 ROWID를 가진다. shadowmsg는 ROWID를 external_id로 사용하므로, 같은 메시지가 서로 다른 external_id로 서버에 2건 저장된다.

서버의 `sha256_hash`는 `external_id|body|sent_at`로 생성하는데, external_id가 다르면 hash도 달라져서 중복 감지가 안 된다.

**오답**: "device prefix를 external_id에 붙이면?" → 이건 오히려 중복을 더 만든다. 문제의 본질은 "같은 메시지에 다른 ID가 붙는 것"이지 "다른 메시지에 같은 ID가 붙는 것"이 아니다.

**올바른 해결**: LuaHome 서버 측에서 sha256_hash를 `body|sent_at|sender`만으로 생성하면 같은 메시지는 어느 Mac에서 보내든 동일한 hash가 된다. shadowmsg 쪽에서는 할 수 있는 게 없음.

**현재 상태**: 미해결. LuaHome 서버 코드 변경 필요.

## mozzi Mac launchd 서비스: Full Disk Access 필요

`tags: deployment, mozzi, launchd, fda, troubleshooting, chat-db`

- `bunx @home/shadowmsg service install`로 launchd 서비스 등록
- exit code 256, "authorization denied" 발생 → **bun에 Full Disk Access(FDA) 필요**
  - macOS가 `~/Library/Messages/chat.db` 접근을 차단

## release.sh와 npm-publish.sh의 역할 구분

`tags: devops, scripts, npm-publish, release, naming`
`files: mise/release.sh, mise/npm-publish.sh`

처음에 publish.sh와 release.sh의 관계가 불명확했다.

- `mise/release.sh` = version bump (package.json + src/app.ts) + git tag + push → GitHub 릴리스
- `mise/npm-publish.sh` = npm publish → public(npmjs.com) / private(npm.app.local) / all
- 별개의 작업. 전형적 흐름: `mise release patch` → `mise npm-publish all`
